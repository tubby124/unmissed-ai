# Harness: cross-check "claimed sent" against actual delivery

## Origin (2026-05-29)

D456 surfaced that `trial-expiry` cron writes `trial_reminder_sent.dayN` JSON flag + fires Telegram "reminder sent" alert without confirming Resend actually delivered. Velly Remodeling: 3 lying alerts in 4 days, 0 real emails.

Fixing that one cron (D456) doesn't catch the next cron that develops the same pattern. The harness pipeline is built for exactly this — catching system-wide drift between "we claim X" and "X actually happened." This adds the missing coverage.

## What this harness validates

For every client + every notification-firing context (welcome, trial-reminder dayN, lead alert, weekly digest, etc.), the harness verifies:

1. **JSON flag → log parity**: if `clients.trial_reminder_sent.dayN` is populated with a timestamp, there must be a `notification_logs` row within ±60 seconds tagged for that client_id and a reminder-type channel.
2. **Telegram alert → log parity**: every Telegram message sent to admin chat claiming "sent to {client}" must reference a real `notification_logs` row (via Resend message_id, Twilio SID, or Telegram chat_id) for that client.
3. **Resend webhook → log parity**: if Resend's webhook archive shows a `delivered` event for a message_id, the corresponding `notification_logs` row should reflect that. Missing webhook→log linkage = also a finding.

## Build

1. New script `scripts/notification-honesty-check.ts`:
   - Pull every `clients` row updated in the last 24h
   - For each, check the three parity rules above
   - Use `recordFindings({ harness: 'notification-honesty', run_id, findings })` via existing `src/lib/harness-writer.ts`
2. New `.github/workflows/notification-honesty-check.yml` — cron `15 10 * * *` UTC (offset from other nightly harnesses), needs Supabase + Resend API secrets
3. Register `notification-honesty` in all three sync points:
   - `HarnessName` union in `src/lib/harness-writer.ts`
   - `VALID_HARNESSES` in `src/app/api/admin/harness/findings/route.ts`
   - `PRETTY_NAME` in `src/components/admin/harness/HarnessCard.tsx`
4. Finding shape:
   - `harness_name: 'notification-honesty'`
   - `check_name: 'trial_reminder_lie' | 'telegram_claim_no_log' | 'resend_event_no_log'`
   - `severity: P0` (silent revenue impact)
   - `client_slug`, `details` with the missing-row context

## Acceptance

- [ ] Harness ships and runs nightly
- [ ] First run flags every existing `trial_reminder_sent.dayN` row that has no matching `notification_logs` row (Velly: 3 findings expected)
- [ ] After D456 ships, re-running the harness on a freshly triggered trial reminder produces zero findings
- [ ] Admin dashboard at `/dashboard/admin/harness` shows `notification-honesty` as a registered harness with its findings count

## Why this matters

Hasan's quote: "What's the point of a harness if it's lying to you?" The harness wasn't lying — it just didn't cover the trial-reminder cron's claim. This closes that gap and prevents the same class of bug from biting silently again. Pair this with D456 (fix the cron) for full coverage.
