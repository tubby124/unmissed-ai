# D427 — End Voicemail launch readiness: replace voicemail activation path

## Summary
End Voicemail's core promise is not just "talk to an agent in the browser." The product must reliably replace a service business's missed-call voicemail by:

- learning the business from Google Business Profile, website, uploaded facts, and manual context
- answering calls when the owner misses or forwards calls
- qualifying the lead and collecting the required sale/context fields
- giving useful caller guidance when the business knowledge supports it
- notifying the owner/receptionist with exactly what to say next
- optionally texting the caller and scheduling/booking when connected

The 2026-05-18 production canary proved the browser/WebRTC agent path works, but it also exposed that a trial can look "active" while not yet being a true voicemail replacement.

## Implemented 2026-05-18
- Onboarding final activation now sends users to the paid activation/Stripe path (`mode="paid"`) instead of the browser-only trial provisioning path.
- Visible onboarding and pricing copy now frames activation as card-upfront with a real AI number and 50 included activation minutes for forwarded-call testing.
- Post-checkout success copy now points users to `/dashboard/go-live` and frames the next action as forwarding calls, connecting alerts, and making a real missed-call test.
- Core `$119/mo` plan display and operational entitlement now match the intended 250 included monthly minutes.
- Legacy trial URLs/screens still exist for backward compatibility and internal testing, but the primary public onboarding path no longer promises "no card required."

## Landing Page CRO Findings 2026-05-18
- Homepage message is emotionally strong but not explicit enough in the first viewport: it says "They called. You didn't answer. We fix that." but does not immediately say "forward missed calls to an AI number that qualifies leads and sends you the summary."
- CTA hierarchy is split: hero primary action is "Call Me Now" demo, while the actual business goal is paid activation. The demo should become secondary; primary should be "Get Your AI Number" or "Start setup."
- Stale contradiction remains on marketing surfaces: navbar says "Sign Up Free" and pricing hero says "No credit card required" even though primary onboarding now requires card-upfront activation.
- Pricing/offer is muddy: homepage leads with `$29/mo`, but the strategic offer is `$119/mo` AI Receptionist with 250 minutes. This can attract the wrong buyer or make the real plan feel like an upsell surprise.
- Trust claims need proof: "8,400+ calls answered" and "2,100+ jobs captured" should be backed by real source/tracking, reframed as demo/system activity, or removed until verifiable.
- The page undersells the actual setup moment: call forwarding, carrier voicemail blockers, alert setup, and the 50 included real test minutes should be part of the main page argument, not hidden after checkout.
- Notification copy should shift from Telegram/SMS-first to email-first with Telegram optional, matching the lower-friction SMB onboarding path.
- Pricing/SEO schema includes hidden/tester pricing in aggregate offers, causing inconsistent low/high price metadata. Marketing schema should only expose public plans.

## Product Requirement
The dashboard should make the difference between "agent exists" and "voicemail replacement is live" impossible to miss.

Define "ready to replace voicemail" as:

1. Agent provisioned and testable.
2. Business knowledge source present: GBP, website scrape, uploaded/imported knowledge, or strong manual description.
3. Call route active: provisioned End Voicemail number OR clear conditional-call-forwarding setup completed.
4. At least one owner notification channel connected: Telegram or email.
5. Test inbound phone call completed through the Twilio/inbound path, not only browser WebRTC.
6. Owner can see call summary/transcript and next-step guidance after the test call.
7. If SMS is advertised/enabled, caller SMS is configured and verified.
8. If scheduling is advertised/enabled, calendar connection is configured and verified.

## Recommended Work

### P0 — Minimum Viable Rollout Without Rebuild
- Do not rebuild the product around the new model yet. Use the existing paid activation path first:
  - `/onboard` collects business setup.
  - `mode="paid"` posts to `/api/provision`.
  - `/onboard/status?id=...` already shows agent preview, number picker, Stripe checkout, and activation-minute copy.
  - Stripe activation provisions/assigns a real number.
  - `/dashboard/go-live` already gives forwarding instructions once `twilio_number` exists.
- Operationally, route ad traffic to the paid activation path and stop emphasizing the free browser-only trial.
- Keep the browser/WebRTC agent test as the preview step: "hear what your agent knows" before the real phone test.
- Use manual/operator support for the first 5-20 customers instead of automating every edge case immediately.

### P0 — Offer Shape To Test
- Primary offer: `$119/mo` plan with real number, 250 included minutes, and first 50 activation/test minutes included.
- Trial framing: "Your first 50 minutes are included so you can test with real forwarded calls."
- Optional bridge: sell a one-time 50-minute test pack only if the user is not ready for the full plan, but avoid making minute packs the main product if flat-rate simplicity is the positioning.
- Number inventory: start with a small pool before buying 50. Increase inventory only when ad conversion and activation completion justify it.
- Refund / cancellation should be crystal clear before checkout, because the customer is taking setup friction risk.

### P0 — Trial / Activation Model Decision
- The WebRTC-only free account is a weak proof of the product because the real product is missed-call replacement, not a dashboard demo.
- Recommended default: require payment method or paid activation before assigning a real number, then include a bounded trial minute allowance.
- Maintain a small number inventory pool so activation is instant, but assign/recycle numbers only after a user has crossed the payment/intent threshold.
- Treat the cost of the number as customer acquisition cost only after the account is ready to run a real forwarded-call test.
- Browser WebRTC should remain as a confidence preview: "hear what your agent knows" before or during activation, not the main trial outcome.
- Product copy should avoid "live" until a real phone route and owner notification path are verified.

### P0 — Activation Truth
- Add a "Replace voicemail readiness" state that is separate from `status=active`.
- Show a hard checklist on dashboard/home or Go Live:
  - Agent tested
  - Business knowledge loaded
  - Phone number or forwarding path set
  - Alert channel connected
  - Real inbound test call completed
- Do not imply the account is fully live when only the browser test has passed.

### P0 — Go Live Becomes The Product
- `/dashboard/go-live` already exists and has carrier-specific forwarding setup plus forwarding verification routes.
- Make Go Live the primary post-purchase activation path, not a secondary dashboard tab.
- Keep the dashboard optional for normal clients. The everyday experience should be: calls get captured, alerts arrive, owner calls back prepared.
- The dashboard's core customer-facing job is setup, agent preview, knowledge edits, and call history — not daily usage.
- After checkout, send users directly to `/dashboard/go-live`, not a generic dashboard page.
- Go Live should say "Step 1: test your agent, Step 2: forward your phone, Step 3: connect alerts, Step 4: make your first real missed-call test."

### P0 — Dashboard Friction To Fix First
- Current free trial success path creates an agent but no number; that is not the real product proof.
- Current Go Live page hides forwarding behind "upgrade" when `twilio_number` is null; for paid activation this is fine, but for free trial users it feels like the product dead-ends.
- Current forwarding setup relies on self-attestation ("It worked — I heard the agent") even though verification infra exists. For early customers, operator-guided verification is acceptable; later, restore real carrier-chain verification.
- Current Go Live notification block is Telegram-first. For SMBs, email should be the default, Telegram optional.
- Current forwarding help should be simplified into one clear decision tree: "heard agent" / "went to voicemail" / "rang forever" / "code failed."

### P0 — Setup Link Reliability
- Investigate the initial trial provisioning setup URL that bounced to `/login`.
- Acceptance: the setup URL returned by `POST /api/provision/trial` establishes a dashboard session in a fresh browser without requiring service-role recovery regeneration.

### P0 — Phone Path Canary
- Create a canary that places or simulates an inbound Twilio call through `/api/webhook/[slug]/inbound`.
- Acceptance: call reaches Ultravox, transcript persists, completed webhook classifies, and the owner notification path fires or correctly reports missing notification setup.

### P1 — Notification Activation
- Make Telegram/email setup a first-class Go Live step.
- If the user chooses Telegram, generate the deep link and verify `telegram_chat_id`.
- If the user chooses email, verify the email notification setting and show where call summaries will arrive.
- Default to email as the lowest-friction alert path; present Telegram/WhatsApp/SMS-style channels as faster optional upgrades.
- Avoid making Telegram mandatory for older/non-technical SMBs.

### P1 — Carrier / Voicemail Friction Handling
- Surface the known blockers before the user dials forwarding codes:
  - carrier voicemail still active
  - iPhone Visual Voicemail / carrier VVM still active
  - plan does not allow external forwarding or needs carrier support
  - user dialed unconditional forwarding when they intended missed-call forwarding, or vice versa
- The repo already has carrier compatibility and voicemail removal UI pieces; consolidate them into the Go Live path.
- Acceptance: a failed forwarding test tells the user the likely cause and the exact next support script to read to their carrier.

### P1 — Lead Qualification Fit
- For service businesses, surface and edit `info_to_collect` during onboarding in plain English.
- Example: plumbing should collect caller name, callback number, address, issue type, urgency, leak/water/heater status, access notes, and best callback time.
- Acceptance: generated prompt and dashboard both reflect the same intake fields.

### P1 — Knowledge + Guidance Boundary
- The agent should answer helpful operational questions only when the knowledge source supports it.
- It should not invent safety instructions. For risky issues, it should use approved business facts or safe generic triage and escalate.
- Acceptance: test calls for plumbing/HVAC/locksmith-like urgent scenarios produce useful intake plus safe escalation.

### P2 — Conversion / Billing Path
- Future paid trial should support credit card upfront, free minutes during trial, auto-renew after trial, and clear cancellation.
- Acceptance: user sees trial minutes, renewal date, plan, and cancellation path before starting.

## Acceptance Test Matrix
- Browser WebRTC fake-mic call: passes and captures both sides.
- Real inbound phone path: Twilio call reaches agent.
- Call forwarding setup: user can follow carrier-specific instructions and mark verified.
- Post-call owner alert: Telegram/email contains lead qualification, urgency, summary, transcript link, and recommended callback opener.
- Caller SMS: sends only when enabled and opted in / compliant.
- Knowledge ingestion: GBP or website content appears in business facts / knowledge chunks and is used by the agent.
- Niche adaptation: plumbing, HVAC, cleaning, real estate, and generic `other` each produce different intake fields and triage rules.
