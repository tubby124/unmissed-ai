# Trial-reminder cron lies to Telegram

## Origin (2026-05-29)

Surfaced while triaging the Velly Remodeling (Kausar Imam) account. Hasan received Telegram alerts on 2026-05-25 (day3 reminder), 2026-05-27 (day1 reminder), and 2026-05-28 (trial expired). Kausar received zero of those emails. Telegram lied; Hasan made business decisions on the lie.

## Evidence

Velly client `088d675c-bd93-4e48-ace6-5a8c6ce9ca68`:
- `trial_reminder_sent.day3` = 2026-05-25 11:15 UTC
- `trial_reminder_sent.day1` = 2026-05-27 10:58 UTC
- `welcome_email_sent_at` = NULL
- `notification_logs` rows for this client_id: **1** (a 2026-05-25 lead alert, not a trial reminder)
- Telegram admin chat received "sent" pings for all three milestones (Hasan confirmed)
- Cross-account Gmail audit (`hasan.sharif.realtor@gmail.com` + `info@true-color.ca`): zero outbound to `kausarimam10@yahoo.com` or `info@vellyremodeling.com` beyond the 2026-04-28 welcome
- `/src/app/api/resend/route.ts` archives Resend webhook events but the cron does not join back to its own claim

## Suspected root causes (both plausible, both fixable)

1. **Flag-before-send race** — cron writes `trial_reminder_sent.dayN = timestamp` + fires the Telegram alert, then the Resend call silently fails (or is never made). The "sent" alert is committed regardless of send outcome.
2. **No delivery confirmation layer** — even when Resend HTTP returns `ok=true`, there is no join between that response and an actual delivery / bounce / complaint event. Telegram trusts HTTP `ok` blindly. No `notification_logs` row is written for trial reminders at all.

## Build

1. Reorder the trial-reminder cron (likely `src/app/api/cron/trial-expiry/route.ts`): call Resend FIRST. Only on `result.ok === true` write the JSON flag + fire the Telegram alert. Telegram message MUST include the Resend `message_id`.
2. Insert a `notification_logs` row for every dayN reminder attempt (success OR failure), keyed by `client_id + reminder_type`. Mirror the existing lead-alert logging shape.
3. Add an `email_delivery_status` field (or extend `notification_logs`) so the existing Resend webhook archive can flip a row to `delivered` / `bounced` / `complained`. Join on Resend `message_id`.
4. Backfill audit: enumerate every `(client_id, reminder_type, JSON-flag-timestamp)` with NO matching `notification_logs` row in the last 30 days. Surface the gap to Hasan so he knows which past Telegram "sent" alerts were lies.
5. Same pattern likely exists for other cron emails (welcome, payment_failed, weekly digest). Broader audit after the trial fix.

## Acceptance

- [ ] Telegram alert for a dayN reminder fires only after Resend confirms `ok` + `message_id` is captured
- [ ] `notification_logs` has one row per attempt (`sent` / `failed_resend` / `skipped`)
- [ ] Bounce/complaint webhook updates the corresponding `notification_logs` row within minutes
- [ ] Backfill report produced: list of clients where Telegram claimed a send that never reached `notification_logs`
- [ ] [[Architecture/Webhook-Security-And-Idempotency]] Section 6 updated with the flag-after-confirm invariant

## Why this matters

This is a trust-of-our-own-telemetry bug. Hasan assumed Kausar was reminded, assumed silence = ghost, and let the trial auto-pause. The truth: zero reminders ever left the building. Any future trial client this fires for will look the same — silent on our side, blameless on theirs, account auto-paused, money left on the table. Velly is the first one we caught only because Hasan was direct enough to ask the recipient.
