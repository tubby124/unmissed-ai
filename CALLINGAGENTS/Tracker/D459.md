# Provisioning-window race on notification dispatch

## Origin (2026-05-29)

Velly Remodeling had 4 calls in a 9-minute window on activation day (2026-04-28 18:02–18:11 Saskatoon). All four were missed by the notification dispatcher despite having no classification gates that should have skipped them. Same pattern likely exists for every new client's first few minutes.

## Suspected race conditions

The provisioning flow does multiple writes that the post-call webhook later reads:

1. `clients.tools` build via `syncClientTools()` (async after provisioning)
2. `clients.ultravox_agent_id` set after Ultravox `createAgent()` returns
3. `clients.twilio_number` set after `ensureTwilioProvisioned()` returns
4. `clients.alert_email` / `alert_phone` / `telegram_chat_id` may be set incrementally as the owner completes onboarding steps
5. `client_users` row may not be linked yet — `client_users.client_id` join fails

If a call lands during step 1–4, the `/completed` webhook reads a partial `clients` row and the dispatcher silently skips channels because credential gates fail (`!alert_email` / `!alert_phone` / `!telegram_chat_id`).

## Diagnose first

Before patching: instrument `sendEmailNotification`, `sendTelegramNotification`, `sendOwnerSmsAlert`, `sendSmsFollowUp` with a single-line structured log when each skips. Include `client.id`, `call_id`, `skip_reason`, and timestamps for `client.created_at` vs `call_log.created_at`. Run for one week, then aggregate skip-reasons by `(call_log.created_at - client.created_at)` delta.

This will tell us empirically whether the race is real and how long the danger window is.

## Build (contingent on diagnosis)

1. Notification dispatcher: when a credential gate fails AND the client was created within the last N minutes (e.g. 15), enqueue a retry rather than silently dropping. Retry once after 60s.
2. Capture every dispatcher skip in a new `notification_skips` table (`call_id`, `channel`, `skip_reason`, `client_age_seconds`, `created_at`) so future audits don't require re-instrumentation.
3. Surface a dashboard banner to the owner during the first hour: "Your account is still wiring up — notifications may be delayed for a few minutes on early calls. Live calls are not affected."

## Acceptance

- [ ] Skip-reason logging shipped, runs for one week, aggregate report produced
- [ ] If race confirmed: retry-after-60s ships and is verified by reproduction (provision client → call within 30s → confirm notification fires)
- [ ] `notification_skips` table populated and indexed by (client_id, channel)
- [ ] Onboarding banner ships
