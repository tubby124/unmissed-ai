# D437 — Learning Loop dashboard patch queue

## Summary
Learning Loop suggestions currently arrive as operator text and rely on manual follow-through. Build a dashboard-backed patch queue so real-call friction becomes reviewable product QA: evidence, proposed fix, risk, regression coverage, approval, application, prompt sync, and audit trail.

## Required
- Add a Learning Loop admin surface in the dashboard, either as a card on Command Center plus a `/dashboard/learning-loop` route or as a subview under Insights.
- Store suggestions durably with status: `suggested`, `needs_review`, `approved`, `applied`, `rejected`, `rolled_back`.
- Each suggestion must include client, call/conversation evidence, failure category, exact caller quote when available, proposed prompt/tool/routing change, risk level, and affected runtime surface.
- Add approval actions: Approve, Reject, Edit, Apply + Sync, Roll Back.
- Require regression evidence before marking `applied`: deterministic test, promptfoo eval, or documented manual smoke depending on risk.
- For prompt changes, show source/runtime drift: repo prompt, `clients.system_prompt`, `business_facts`, `extra_qa`, and relevant knowledge chunks when applicable.
- Never auto-apply high-risk changes that affect legal/compliance, pricing, outbound human contact, calendar booking, transfers, billing, or client-specific policy.
- Emit operator alerts when a high-confidence recurring issue crosses threshold, but keep final application human-approved.

## Acceptance
- Hasan can open the dashboard and see pending Learning Loop suggestions with evidence and risk.
- A suggestion like the booking nonsense case shows: friction call evidence, proposed rule, exact regression phrase, test status, and current deployment/prompt version.
- Applying an approved low-risk prompt patch records who/when/what changed and the resulting prompt version.
- Rejected suggestions remain searchable with rejection reason.
- The queue prevents duplicate suggestions from the same failure pattern.
- Dashboard clearly separates `detected`, `approved`, `applied`, and `deployed/synced` so we do not confuse a recommendation with production behavior.
